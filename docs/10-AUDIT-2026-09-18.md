## 1. THE BIG ONE · the timer stops when you leave its screen — **FIXED 2026-09-18**

**Measured, not inferred.** `scripts/device/s6_audit_background.py`:

```
session open for   ~3 minutes   (timer started, screen left immediately, waited 150s)
sheet offered       1 minute
```

The recovery bound froze at the moment the screen was left, not at the moment of the kill.

**Why.** `useTimer` owns all four moving parts — the tick, the heartbeat, the notification
refresh, and the notification's action listener — and it is called from `TimerScreen`.
Navigating back unmounts the screen, React cleans up every effect, and all four stop. The
`sessions` row stays open and the segments stay on disk, so the NUMBERS remain correct; what
stops is everything that maintains the session while it runs.

**What actually breaks for a reader:**

| They do this | What happens today |
|---|---|
| Start a timer, press Back, put the phone down | Heartbeat stops. A later crash is bounded at the moment they left, so the app offers far less time than they read |
| Tap **Pause** in the notification while elsewhere in the app | Nothing. The listener is unmounted |
| Read for an hour with the app backgrounded | The notification still says the elapsed time from when they left the screen |
| Swipe the app away from Recents | The service keeps the process alive — and nothing is running in it |

**Why no check caught it.** Every automated check drives the timer *from the timer screen*
and never leaves. The arithmetic is genuinely right, so 478 node tests, 15/15 mutations and
six emulator scripts all pass while the feature does not work in the way it exists to work.
This is silent-pass item 20's shape again — **a thing that is correct and not connected**.

**The fix, specified.** Hoist the timer's runtime above the screen:

- A module-level singleton or an app-level provider mounted in `src/app/_layout.tsx` owns the
  current run, the heartbeat interval and the notification, and survives navigation.
- `TimerScreen` becomes a *view* onto it: it reads state and sends intents (pause, resume,
  finish) and owns no interval.
- The notification action listener registers once, at app level, so Pause works from anywhere.
- The heartbeat keeps beating for as long as a session is open, which is what
  `domain/timerRun.ts` has always assumed.

**FIXED.** `features/timer/timerService.ts` now owns the runtime; `useTimer` is a
`useSyncExternalStore` view that owns nothing. The same experiment that found this now reports
the heartbeat tracking the kill rather than the exit (3 minutes open, 2 minutes offered). The
rewrite introduced one regression — a frozen on-screen clock, because the tick did not replace
the snapshot object — which the emulator checks caught and which is fixed. All four suites
pass. Original note follows.

**Do this BEFORE the phone session.** Run-sheet item 1 — start a timer, lock the phone, pocket
it for 20 minutes — would fail today for this reason, and we would learn nothing about the
thing it is designed to measure. **Fixing this is what makes tomorrow's test meaningful.**

## 2. Architecture conformance · mechanically clean

Checked by grep across `src/`, not by reading:

| Rule | Result |
|---|---|
| Features never import from other features | **clean** (two violations introduced and fixed during this audit) |
| All SQL in `queries.ts` / `db/` | **clean** — no `getDb()` outside them |
| No `any` | **clean** |
| No hardcoded colours or bare spacing values | **clean** in slices 5, 5b, 6 |
| Every write through `db/write.ts` | **clean**, held by `no-bypass.test.ts` |
| Timestamps UTC ms, dates only in `lib/dates.ts` | **clean** |

**Two boundary violations were introduced and fixed today**, both by the same pressure — a
second feature needing something a first feature owned:

- `features/launch` could not reach `features/timer`'s heartbeat maths → `timerState.ts` and
  `timerRun.ts` moved to `domain/`. **That misplacement is why the heartbeat was never
  wired**: the call was not merely forgotten, it was forbidden.
- `features/launch` could not reach the timer's notification to clear it after a crash →
  moved to `ui/timerNotification.ts`, following `ui/datePicker.ts`.

**The lesson worth keeping:** in this codebase a missing call is often a misplaced module.
When something cannot be wired, check whether the architecture is forbidding it before
assuming someone forgot.

**Files over the 200-line guide** (a smell detector, not a law): `FinishScreen` 346,
`NoteEditorScreen` 301, `NotesScreen` 239, `timer/queries.ts` 240, `TimerScreen` 216. Each is
one screen or one feature's SQL. Acceptable; `NoteEditorScreen` is the one to watch.

## 3. Premortem · what kills this if nothing changes

Ordered by expected damage.

### 3.1 The timer ships behaving like a stopwatch you must stare at
Finding 1. Readers start a timer and leave the app — that IS the use case. They come back to
an under-counted session, or a notification frozen at 00:02. **This is the one that produces
one-star reviews about wrong numbers**, which is the exact failure `01-PRODUCT.md` says this
product exists to avoid. *Fix before the phone session.*

### 3.2 An open timed session syncs to the server (Slice 8)
`sessions` is syncable, and a running timer is a row with `duration_seconds IS NULL`. When
sync lands, that row reaches the server and then another device — which will see it as "a
session still running" and offer its owner a recovery sheet for a timer running on a different
phone. **Decide in Slice 8:** either open sessions are excluded from the queue until they
close, or the pull side ignores open rows it did not originate. Neither is built.

### 3.3 A book deleted while its timer runs
Still the unanswered question in `04-SCREENS.md`. Deleting a book cascades to its sessions, so
the open timed session is soft-deleted underneath a running timer. The screen keeps ticking;
Finish will be refused by the parent guard and surface as an inline error. Not data loss, but
undefined and unverified. **Decide and test it on the phone.**

### 3.4 `metadata_cache` has no purge — **FIXED 2026-09-19**
**`sweepLocalRecords` runs once at launch**, removing only records whose subject cannot come back and never touching a draft for a live book. Held by device check 20, watched failing both ways.
Note drafts and timer runs are cleaned on their happy paths, and one orphan is already known
(from a session discarded before the cleanup existed). Nothing sweeps the table. Small and
slow-growing, but it is the sort of thing that is much cheaper to fix now than at 50k rows.
**Filed against Slice 8**, which builds the 30-day purge anyway.

### 3.5 The device pass does not cover the timer at all — **FIXED 2026-09-19**
**Checks 19 and 20 added**, each watched failing twice. 19 holds the open/closed shape the recovery gate depends on and that heartbeats queue nothing; 20 holds the sweep. Device pass now RUNTIME 37/38, the one failure being the network-dependent `14c` on an emulator.
36 checks, none about timed sessions. The timer writes to `sessions` through the real write
path, so the class of bug device checks exist to catch applies to it. **Add checks 19 and 20:**
a timer's row is written at Start with the right shape; finishing writes a duration and
queues exactly one upsert.

### 3.6 The clock is the app's largest text, and unseen at scale
`displayLg` is 68px. At 200% font on a 360dp screen it is the most likely thing in the app to
overflow, and it has only ever been seen on a 1080p emulator at default scale.

### 3.7 The APK budget is still a measured problem
112 MB universal against a 15 MB target, and `expo-notifications` has just been added. Filed
against Slice 11; not worse today, but not better.

### 3.8 Two open sessions would be handled two ways — **FIXED during the audit**
Fixed during this audit — both sides now take the OLDEST — but the rule is duplicated in two
features rather than shared. If a third caller appears it belongs in `db/` beside
`currentRead.ts`.

## 4. Code audit · what is genuinely good

Worth recording so it is not undone later:

- **Elapsed time is derived from timestamps, never counted.** This is the single best decision
  in the slice and it is what keeps the numbers right despite finding 1.
- **Every span clamps at zero.** A backwards clock cannot produce a negative duration.
- **The session row is written at Start**, so a crash one second in loses nothing.
- **Device state is local-only by construction.** Drafts and timer runs live in
  `metadata_cache`, which is absent from `SYNCABLE`, so a 30-second heartbeat cannot flood
  `sync_queue`. A comment would not have held this; the registry does.
- **`domain/` is doing real work** — `timerState`, `timerRun`, `noteForm`, `noteDraft`,
  `finishForm` are all pure and heavily asserted, which is why the mutation sweeps are
  meaningful.
- **Notes attach to the book, not the read**, and `notes` is deliberately not a cascade child
  of `reads`. Device check 17 holds it in the direction that can fail silently.
